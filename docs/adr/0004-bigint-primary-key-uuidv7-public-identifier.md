# ADR 0004 — کلید اصلی BIGINT و شناسه عمومی UUIDv7

تاریخ: 2026-10-12
وضعیت: پذیرفته
جایگزین می‌کند: بند شناسه ADR 0001. بقیه ADR 0001 پابرجاست.

## Context

نسخه اول کلید اصلی مدل‌های دامنه را UUIDv7 گذاشته بود و نام ستون را `id` نگه داشته بود. همان مقدار هم کلید خارجی بود و هم شناسه URL. ADR 0001 این را ثبت کرده بود.

برای رابطه داخلی، کلید ۸ بایتی `bigint` از کلید ۱۶ بایتی `uuid` جمع‌وجورتر است و درج ترتیبی identity با btree کلید اصلی سازگارتر است. شناسه عمومی همچنان نباید ترتیب ردیف را لو بدهد و نباید با شناسه GitHub/GitLab یکی شود. UUID مجوز دسترسی نیست.

پایگاه توسعه `rahandaz` روی PostgreSQL 16.15 پیش از تبدیل، کلید `users.id` از نوع `uuid` داشت و تنها جدول غیرخالی‌اش `migrations` با ۱۴ ردیف بود. `users` و `credentials` صفر ردیف داشتند. migrationهای قبلی در git ثبت شده بودند. `migrate:fresh` روی این پایگاه اجرا نشد.

## Decision

- کلید اصلی هر مدل اصلی دامنه `id` از نوع `bigint` و `GENERATED BY DEFAULT AS IDENTITY` است. Laravel این را با `$table->id()` می‌سازد. identity سفارشی جدا تعریف نشده است.
- ستون `uuid` از نوع native `uuid`، `UNIQUE` و `NOT NULL` است. مقدارش UUIDv7 است. کلید اصلی نیست و `varchar(36)` نیست.
- کلید خارجی داخلی `bigint` است و با `foreignId()` ساخته می‌شود. `foreignUuid()` برای رابطه داخلی معمول استفاده نمی‌شود.
- رابطه Eloquent پیش‌فرض روی `id` است. `getKeyName()` همان `id` می‌ماند. `HasUuids` کلید اصلی را عوض نمی‌کند.
- API، URL و props عمومی Inertia شناسه `uuid` را می‌فرستند. `id` عددی در JSON عمومی نیست. در صف، شناسه داخلی اگر لازم باشد رشته دهدهی است، نه عدد JSON.
- تولید در مدل با `App\Models\Concerns\HasPublicUuid` و `App\Support\Identifiers` است. `Identifiers` از `Str::uuid7()` نسخه نصب‌شده Laravel استفاده می‌کند. trigger `rahandaz_guard_public_uuid` مسیر bulk insert و Query Builder را می‌پوشاند، چون رویداد مدل آنجا اجرا نمی‌شود.
- `uuid` بعد از ایجاد عوض نمی‌شود. درخواست عمومی نمی‌تواند آن را mass-assign کند. import مورد اعتماد می‌تواند پیش از اولین save یک UUIDv7 معتبر بگذارد.
- `id` داخلی، `uuid` عمومی و شناسه provider سه ستون مستقل‌اند.

## Alternatives

- ماندن روی UUIDv7 به‌عنوان کلید اصلی و کلید خارجی. رد شد: هدف این تصمیم جدا کردن شناسه عمومی از کلید رابطه است.
- `uuid` به‌صورت `varchar(36)`. رد شد: PostgreSQL نوع native `uuid` دارد و مقایسه و ذخیره متنی لازم نیست.
- تولید UUIDv7 فقط داخل PostgreSQL. نسخه ۱۶ تابع داخلی `uuidv7()` ندارد. تولید در PHP با trigger نگهبان انتخاب شد تا نصب تازه و درج Query Builder هر دو پوشش داده شوند.
- `HasUuids` لاراول. آن trait کلید اصلی را uuid می‌کند و با این قرارداد ناسازگار است.

## Performance Tradeoffs

کلید اصلی و کلید خارجی باریک‌تر می‌شوند و شناسه عمومی فقط یک ایندکس یکتا اضافه می‌کند. این دلیل طراحی است، نه نتیجه اندازه‌گیری.

`EXPLAIN (ANALYZE, BUFFERS)` اجرا نشد. جدول‌های دامنه صفر ردیف داشتند و مقایسه UUID در برابر BIGINT روی این حجم بی‌معنا بود. بهبود سرعت ادعا نمی‌شود. ایندکس بزرگ بعدی همچنان باید بیرون از transaction و با `CREATE INDEX CONCURRENTLY` بررسی شود.

## Migration Strategy

دو مسیر هم‌زمان است.

نصب تازه و پایگاه آزمون `rahandaz_test` از متن بازنویسی‌شده migrationهای ایجاد جدول، مستقیم `id` عددی و `uuid` عمومی می‌سازند. تاریخچه git با amend عوض نشده است. `RefreshDatabase` فقط پایگاه آزمون را از نو می‌سازد.

پایگاه توسعه که migrationهای uuid را قبلاً ثبت کرده بود با `2026_10_12_120000` و `IdentityCutover` جلو می‌رود. اگر `users.id` از قبل `bigint` باشد migration برمی‌گردد. وگرنه uuid قبلی را در ستون `uuid` کپی می‌کند، `id` جدید تخصیص می‌دهد، کلید خارجی را از روی نگاشت پر می‌کند، constraint و ایندکس را دوباره می‌سازد و تعداد ردیف را با قبل مقایسه می‌کند. UUID موجود regenerate نمی‌شود. `down()` استثنا می‌دهد؛ برگشت فقط از backup است.

روی `rahandaz` این تبدیل در 2026-10-12 به‌صورت forward اجرا شد. پیش و پس از آن ردیف دامنه صفر بود و `migrations` از ۱۴ به ۱۶ رسید. یک dry-run قبلی داخل transaction برگشت داده شده بود و اسکیما را uuid باقی گذاشته بود؛ migrate واقعی بعد از شمارش دوباره ردیف‌ها اجرا شد. `migrate:fresh` و `db:wipe` روی `rahandaz` اجرا نشدند.

اگر پایگاه بعدی ردیف داشته باشد، همین cutover مقدار uuid موجود را نگه می‌دارد. اگر آن مقدار نسخه ۷ نباشد، trigger بعدی هر update آن ردیف را با `23514` رد می‌کند، چون نسخه را روی هر نوشتن بررسی می‌کند. بدون تصمیم سازگاری، UUID موجود regenerate نمی‌شود. تغییر کلید اصلی روی پایگاه دارای ترافیک واقعی همچنان تأیید جدا می‌خواهد. قفل DDL و ترتیب استقرار کد و migration در آن حالت باید جدا سنجیده شود. این اجرای توسعه قفل قابل‌توجهی نداشت چون جدول‌ها خالی بودند.

ریسک باقی‌مانده cutover: نگاشت والد از اولین FKای که ستون مقصدش `id` است استفاده می‌کند. در کاتالوگ قبلی تنها FK بدون مقصد `id` ستون `audit_events.prev_hash` بود و آن ستون تبدیل نمی‌شود. پس از migrate، ۱۲۶ کلید خارجی برگشتند. این را جدول خالی برای والد اشتباه اثبات نمی‌کند.

## Security Implications

پنهان کردن ترتیب `id` در URL کنترل دسترسی نیست. Policy و عضویت workspace جدا هستند. مسیر آزمایشی `GET /rahandaz/projects/{project}` مدل را با `uuid` پیدا می‌کند، `id` عددی را در JSON نمی‌گذارد، شناسه غیر v7 را ۴۰۴ می‌کند و پروژه workspace دیگر را ۴۰۳ می‌کند.

AAD پاکت credential و ایندکس کور از نمایش دهدهی `workspaces.id` استفاده می‌کنند. چون صفر ردیف credential وجود داشت، پاکت قبلی شکسته نشد. ردیف‌های بعدی با همین قرارداد ساخته می‌شوند. عوض کردن دوباره ورودی AAD بدون شمارش `credentials` و برنامه rewrap ممنوع است.

`audit_events.resource_id` خود `uuid` عمومی منبع است، نه `id` عددی. دانستن این مقدار همچنان مجوز خواندن منبع نیست.

## Consequences

مدل‌های دامنه `HasPublicUuid` دارند. Route عمومی `getRouteKeyName()` را `uuid` برمی‌گرداند، مگر `#[RouteKey]` لاراول ۱۳ صریحاً چیز دیگری بگوید. نشست همچنان `id` عددی کاربر را نگه می‌دارد.

نصب تازه و آزمون PHPUnit این اسکیما را از migrationهای ایجاد جدول می‌سازند. خود suite مسیر cutover را اثبات نمی‌کند، چون روی نصب تازه `120000` بی‌اثر است. dry-run برگشتی و migrate واقعی پایگاه خالی `rahandaz` آن SQL را اجرا کردند.

کد داخلی بعد از resolve کردن `uuid` با `id` عددی join می‌کند. جایگزین کردن بی‌دلیل کلید خارجی با uuid ممنوع است.

## Exceptions

این جدول‌ها شناسه دوتایی دامنه نمی‌گیرند و اسکیمای رسمی‌شان برای یکسان‌سازی عوض نشده است:

- `sessions`، `cache`، `cache_locks`، `jobs`، `failed_jobs`، `job_batches`، `password_reset_tokens`
- pivot بدون هویت مستقل. در اسکیمای فعلی چنین جدولی نیست. `memberships` و `resource_grants` هویت مستقل دارند و هر دو شناسه را دارند.
- جدول داخلی package، اگر بعداً اضافه شود

استثنای نوعی، نه استثنای حذف `uuid` عمومی:

- `sessions.user_id` باید نوع `users.id` را دنبال کند و `bigint` است. خود `sessions` ستون `uuid` عمومی ندارد.
- `failed_jobs.uuid` همان `varchar` لاراول است و trigger نسخه ۷ روی آن نیست.
- `audit_events.resource_id`، `audit_events.request_id`، `audit_events.correlation_id` و `credential_access_events.request_id` native `uuid` می‌مانند و کلید خارجی عددی نیستند.
- `remote_repositories.provider_repository_id` و شناسه‌های مشابه provider نوع خودشان را دارند.
