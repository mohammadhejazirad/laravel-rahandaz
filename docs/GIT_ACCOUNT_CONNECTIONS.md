# اتصال حساب‌های گیت

صفحه ابتدا حساب‌های متصل و «افزودن حساب» را نشان می‌دهد. افزودن حساب در پنجرهٔ مرحله‌ای انتخاب سرویس ← تأیید حساب ← انتخاب مخزن‌ها انجام می‌شود. تنها فرم سرویس انتخاب‌شده دیده می‌شود؛ تنظیمات OAuth در بخش پیشرفته‌اند. تاریخچهٔ کامل زمان‌دار جمع‌شونده است و هنگام صفحه‌بندی تاریخچه باز می‌ماند. کلید مشترک یا سرویس واسط وجود ندارد.

ورودی پنل: `/rahandaz/git` با base path قابل تنظیم. مالک/مدیر Workspace می‌تواند برنامهٔ اتصال را تنظیم، حساب را متصل، مخزن را مجاز، sync را درخواست یا دسترسی محلی را قطع کند. سایر اعضا تنها اتصال دارای ResourceGrant مشاهده را می‌بینند؛ این grant اجازهٔ رمزگشایی توکن یا تغییر دسترسی نمی‌دهد.

## قرارداد اتصال

GitHub از GitHub App user authorization استفاده می‌کند؛ private key/JWT یا نصب privileged روی میزبان لازم نیست. در نصب بدون برنامه، GitHub App Manifest برنامهٔ اختصاصی را با تأیید کاربر در GitHub می‌سازد؛ Client ID، Client Secret و slug مستقیم در Backend دریافت می‌شوند و کپی‌کردن دستی لازم نیست. manifest مجوز فقط‌خواندنی Contents/Metadata و webhook غیرفعال دارد (URL الزامی webhook برابر صفحهٔ اصلی است و هیچ delivery فعال نیست). برنامه خصوصی و متعلق به حساب سازنده است؛ برای برنامهٔ سازمانی یا موجود، مسیر تنظیم پیشرفته حفظ شده است. کلید خصوصی و webhook secret برگشتی نگهداری نمی‌شوند، چون این جریان user authorization است. Manifest به نشست، کاربر، Workspace و state تصادفی ده‌دقیقه‌ای متصل است؛ کد فقط یک بار با endpoint ثابت GitHub مبادله و راز رمزگذاری می‌شود. برنامهٔ موجود بی‌صدا جایگزین نمی‌شود. پس از ثبت، کاربر مستقیم به نصب برنامه و انتخاب دسترسی‌ها می‌رود. شکست ساخت با پیام ثابت و audit بدون پاسخ خام گزارش می‌شود. تنظیم دستی Client ID، Client Secret و slug هم در بخش پیشرفته باقی است. Callback و Setup URL برابر آدرس نمایش داده‌شده در پنل‌اند. Request user authorization during installation باید خاموش باشد تا مرحلهٔ نصب و OAuth به ترتیب مدیریت شوند؛ Redirect on update روشن باشد. برنامه فقط Contents/Metadata فقط‌خواندنی داشته باشد. کاربر در GitHub گزینهٔ Only select repositories را انتخاب می‌کند. پس از نصب، state تازه برای OAuth ساخته، هویت کاربر، مالک نصب، app slug، permissions و امکان خواندن repositoryهای نصب بررسی می‌شوند. اتصال هر مالک/سازمان مستقل است.

GitLab.com برای شروع سریع، ساخت توکن فقط‌خواندنی را با لینک مستقیم و scopeهای پیشنهادی ارائه می‌کند. GitLab API عمومی معادل Manifest برای ساخت خودکار OAuth Application این نصب ندارد؛ اتصال مرورگری پس از تنظیم یک‌بارهٔ برنامه توسط مدیر در دسترس است. GitLab.com با Confidential OAuth Application و scopeهای `read_user read_api read_repository` متصل می‌شود. انتخاب مخزن در پنل scope توکن GitLab را تغییر نمی‌دهد؛ این محدودیت در رابط نوشته شده است. GitLab شخصی با گزینهٔ سوم `gitlabSelf`، برنامهٔ OAuth مستقل و origin HTTPS عمومی ثبت‌شده پشتیبانی می‌شود. آدرس ثبت‌شده allowlist همان Workspace است؛ endpointهای OAuth/API/refresh فقط روی همان origin ساخته می‌شوند. HTTPS بدون userinfo، مسیر، query یا پورت سفارشی الزامی است؛ IP خصوصی/داخلی و DNS عمومی با مقصد خصوصی رد می‌شوند. تغییر origin با اتصال فعال رد می‌شود و پس از قطع اتصال هم راز برنامهٔ سرور جدید لازم است. GitLab عمومی و شخصی در مدل دامنه هر دو `gitlab` هستند، چون API یکسان دارند؛ کلید `gitlabSelf` برای تنظیمات و رابط است و `base_url` آن‌ها را مستقل می‌کند.

هر دو جریان state یک‌بارمصرف، اتصال به session/user/workspace، انقضای ۱۰ دقیقه و PKCE S256 دارند. Callback به همان نشست معتبر نیاز دارد. نشست production باید HTTPS امن داشته باشد و APP_URL / آدرس reverse proxy درست باشد. Client Secret در Credential رمزگذاری‌شدهٔ Workspace ذخیره و تنها هنگام ارسال به endpoint ثابت HTTPS در body استفاده می‌شود؛ در URL، props یا audit نیست. access/refresh tokenها نیز در Credential رمزگذاری می‌شوند. تمدید پیش از انقضا با قفل انجام می‌شود. تغییر client id یا لغو مجوز ممکن است اتصال مجدد را لازم کند.

## انتخاب و همگام‌سازی

جست‌وجوی نام مخزن سمت سرور، حساس‌نبودن به حروف، تطبیق لفظی و صفحه‌بندی ۵۰تایی دارد. انتخاب همه یا پاک‌کردن انتخاب‌ها فقط همان صفحه را تغییر می‌دهد؛ archived/disabled قابل انتخاب نیستند. نوار ذخیره وضعیت تغییرات ذخیره‌نشده را نشان می‌دهد؛ پیش از جست‌وجو یا تغییر صفحه باید ذخیره کرد.

`is_selected` پیش‌فرض false است و `disabled` دسترس‌پذیری مشاهده‌شده از سرویس را مشخص می‌کند. فهرست کامل تا سقف ۱۰۰ صفحهٔ ۱۰۰تایی خوانده می‌شود؛ افزایش بیش از سقف خطا دارد و بی‌صدا truncate نمی‌شود. شکست API، احراز یا payload به ذخیرهٔ ناقص منجر نمی‌شود. انتخاب موجود برای مخزن‌های حاضر حفظ و انتخاب مخزن حذف‌شده یا archived غیرفعال می‌شود. disconnect هم انتخاب‌ها را حذف و اعتبارنامهٔ محلی را revoke می‌کند؛ مجوز واقعی سرویس جداگانه لغو می‌شود. اتصال مجدد همان UUID حساب را حفظ می‌کند و انتخاب قبلی را خودکار برنمی‌گرداند.

خواندن شاخه و مسیر ثبت deployment برای مخزن متصل، انتخاب صریح و اتصال فعال می‌خواهند. این برش به‌تنهایی پروژه جدید، deploy key، webhook یا اجرای میزبان ایجاد نمی‌کند. موتور عملیات disabled باقی است.

`SyncGitRepositories` فقط UUID اتصال و کاربر را به صف `control` می‌فرستد؛ unique، یک تلاش، timeout برابر ۶۰ ثانیه و timeout کمتر از retry_after پیش‌فرض ۹۰ ثانیه است. worker باید فعال باشد. مجموعهٔ خیلی بزرگ یا شبکهٔ کند ممکن است از timeout عبور کند و نیاز به محدودکردن مجوز سرویس داشته باشد. درخواست ثبت‌شده موفقیت sync نیست؛ تاریخچه نتیجهٔ واقعی را نشان می‌دهد. exceptionهای HTTP با پیام ثابت جایگزین می‌شوند؛ پاسخ خام/توکن در failed job ذخیره نمی‌شود.

## رویدادها و آزمون

Audit زنجیره‌دار موجود استفاده می‌شود: تنظیم برنامه، شروع/رد/شکست مجوز، بازگشت نصبِ هنوزتأییدنشده، اتصال موفق، درخواست/شروع sync، هر صفحهٔ API، نتیجه، تغییر مجوز هر مخزن و قطع اتصال. تاریخ UTC ذخیره و با timezone کاربر به جلالی نمایش داده می‌شود. تاریخچه صفحه‌بندی دارد و راز یا body سرویس را برنمی‌گرداند.

آزمون‌های `tests/Feature/GitAccountsTest.php` با PostgreSQL مجزای `rahandaz_test` و `Http::fake` هستند؛ هیچ حساب بیرونی یا دسترسی واقعی ساخته نشده است. آزمون زندهٔ OAuth/refresh در GitHub/GitLab و مرور بصری viewportها همچنان لازم است. این برش گواهی production-ready یا VM برای Ubuntu نیست؛ installer/Bash/عملیات سیستم تغییر نکرده‌اند.

## اتصال دستی و تست اتصال

برای هر سه سرویس، در راهنمای افزودن حساب، اتصال دستی با توکن محدود وجود دارد. «تست اتصال دستی» هویت و دسترسی خواندن فهرست مخزن‌ها را از API همان origin بررسی می‌کند و توکن را ذخیره نمی‌کند. «اتصال و ذخیرهٔ توکن» ابتدا همین بررسی را انجام و سپس Credential رمزشده و اتصال را ثبت می‌کند؛ دریافت فهرست در صف انجام می‌شود. توکن محدود به ۲۵۵ نویسه و بدون whitespace است. برای GitLab شخصی، نشانی HTTPS مستقل با همان محدودیت‌های SSRF لازم است.

«تست مسیر اتصال خودکار» فقط دسترس‌پذیری صفحهٔ مجوز را با endpoint ثابت، DNS بررسی‌شده، بدون دنبال‌کردن redirect و بدون ارسال Client Secret بررسی می‌کند. این تست اعتبار Client Secret، هویت حساب یا تکمیل OAuth را ادعا نمی‌کند؛ متن رابط و پیام نتیجه همین محدودیت را نشان می‌دهند.

پس از اتصال دستی یا OAuth، در صفحهٔ حساب «تست اتصال» موجود است: اعتبارنامه باز و در صورت لزوم تمدید می‌شود، هویت و فهرست مخزن قابل خواندن بررسی و نتیجه در audit ثبت می‌شود. هویت توکن شخصی باید با حساب ذخیره‌شده تطابق داشته باشد؛ برای GitHub App دسترسی installation بررسی می‌شود. اتصال revokeشده تست نمی‌شود و هیچ تستی انتخاب مخزن‌ها را تغییر نمی‌دهد. تست‌ها محدودیت تعداد درخواست، مجوز مدیر و کنترل Workspace دارند. پاسخ خام، header احراز یا توکن در نتیجه/تاریخچه نیست.


## مرجع پروتکل ساخت خودکار

قرارداد Manifest با [مستند رسمی GitHub](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest) تطبیق داده شد. آدرس بازگشت باید از مرورگر همان کاربر قابل دسترسی و APP_URL/proxy صحیح باشد؛ قبول URL توسط GitHub و نشست واقعی همچنان نیازمند آزمون زنده‌اند. این قابلیت clone/deploy پروژه یا مدیریت چندسرور اضافه نمی‌کند.
