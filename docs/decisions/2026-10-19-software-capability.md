# Initial setup and restricted software installation

Owner decision on 2026-10-19: complete initial setup and real software installation from the panel before the wider deployment engine. This authorizes this specific capability; the general `ExecutionGate` remains closed and `RAHANDAZ_EXECUTION_MODE=disabled` remains the default.

The initial release of this capability permits `setup.initialize` and `software.install` only, with the fixed catalog in `infrastructure/operations/software/catalog.json`: htop, jq, FFmpeg and Unzip on Ubuntu 22.04/24.04. Ubuntu 26.04 is refused. It does not enable runtime, database, deployment, mirror, firewall, SSH or arbitrary package operations. Chrome remains optional and is not installed by bootstrap, upgrade, setup or this catalog. Its GUI installation remains unavailable until its separate binary/render contract is implemented.

HTTP validates the workspace, owner/admin membership, selection and idempotency key and records Job/Outbox/Audit. Only the initial workspace owner may initialize. The control worker uses a fixed JSON client and a separately enrolled root-owned Unix socket helper. The helper checks the exact service UID via SO_PEERCRED, UUIDv7, catalog allowlist, immutable code ancestors, root-private state, and a fresh database job/actor/workspace/host/plan authorization executed with direct service UID/GID reduction, no supplementary groups and an explicit positive JSON proof. PAM/runuser is not used in the hardened helper. Socket group membership alone is insufficient. No sudo policy or free shell is introduced.

The helper acknowledges before doing long work; a systemd instance owns the process group, with a 900-second deadline. Each download/apply has a 90-second limit, and real APT lock waiting is bounded to 30 seconds. The PHP client timeout is 8 seconds and its Process limit is 12 seconds, below the existing 60-second control worker and 90-second Redis retry_after. A durable outbox schedules reconciliation; the existing minute scheduler may add up to a minute of progress latency. A lost worker reuses the same execution UUID and private root journal. Boot ID, PID start time and a global flock prevent blind duplicate execution. An orphan is reported as interrupted. Failed jobs need a new, explicitly confirmed request; APT's authenticated download cache is reused. There is no claim of exactly-once delivery.

APT simulation refuses removal or any upgrade of an installed dependency. Every newly resolved package/dependency version is pinned in the private execution plan, authenticated download happens first, authorization is checked again, and the plan is simulated again before apply with all pins explicitly named and `--no-upgrade --no-remove`. Existing tools are observed, not upgraded. Verification checks dpkg installed/version plus the fixed root-owned executable's version command. Broken/interrupted foreign dpkg state is refused; locks are never deleted, and `dpkg --configure -a` or automatic system repair is never silently run. APT package installation is not transactionally reversible: an interrupted/failed multi-package operation may leave earlier packages installed. The panel reports failure and permits a fresh plan; it does not remove those packages as rollback.

Before and after installation, verify Ubuntu, locked non-login service identity without privileged groups, NoNewPrivileges on FPM/queue, required systemd units, the service-user doctor (DB/Redis/keys/PHP/timing), and actual HTTP /up and login responses. Every required systemd unit is checked separately; a multi-unit `is-active` result only proves that at least one unit is active. Setup completes only with verified control-plane evidence and every selected tool verified. The setup session, answers, required/optional components, plan hash and job remain durable; failed mandatory or optional work stays blocked. The owner may retry with a corrected selection, including explicitly skipping all optional tools. This does not mark an OS globally `supported`, prove project isolation/UID provisioning, or declare production readiness. Host facts retain `untested` compatibility.

The normal setup UI shows measured server facts, selection, review, progress, actionable errors and a real finish link. The global internal execution-disabled banner is removed; unavailable capabilities remain identified at their own controls. Advanced eight-stage onboarding, exact dependency/download-size preview before owner confirmation, welcome-project provisioning and SSH hardening remain separate work in PROJECT_SPEC. The current review authorizes only the listed tools from the already configured signed APT source; the exact dependency plan is pinned by the root helper before mutation and is not yet returned for a second GUI approval.

Enrollment runs from the verified signed release as root during installer stage 12, or during a supervised signed upgrade. It refuses foreign systemd files and unsafe paths. It installs only the helper/socket, never optional software. Shell source, prompts and comments remain English ASCII.

Validation: see `docs/SOFTWARE_SETUP_TEST_REPORT_2026_10_19.md`. Containers verify contracts and actual APT tools; a real VM must verify socket activation, service isolation, queue and panel completion. None of this certifies the unfinished general operations engine or all three Ubuntu targets.

Live Ubuntu 24.04 diagnosis: explicit `User=root` combined with `NoNewPrivileges` in a systemd service removed effective CAP_SETUID and prevented service-identity reduction. This was reproduced using otherwise identical transient services, with and without that directive. The software unit uses the default system-service root identity; the helper still requires effective UID 0. NoNewPrivileges and all other hardening remain enabled. Direct UID/GID reduction and read-only readiness passed under the final property set. A failed authorization subprocess is reported as AUTHORIZATION_CHECK_FAILED, without exposing stderr. Failed setup sessions remain visible and are not replaced by automatic saving until an explicit edit/save. Signed beta34 subsequently passed real GUI setup, natural worker/socket execution, verified completion and dashboard entry on Ubuntu 24.04; the linked test report records scope and remaining coverage.
